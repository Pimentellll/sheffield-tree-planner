**Rule:** a statement in the video, form, README or Q&A must match an **approved** row. VR rows are approved. An RI row is approved for general statements about the code; an on-screen or narrated instance of it is approved only when every acceptance row in its "Needs Spark?" cell is `verified`. An SE row is approved only when every acceptance row it cites is `verified`. Rows in HF may be said only as plans. Rows in UP must not be said; use the safer wording. **Composite categories:** `A + B` means both conditions must hold (for example, O-02 needs the code row and its Spark row). `X → Y (condition)` means the row is X now and becomes Y only when the condition is evidenced; until then treat it as X. A **Rule** row states an obligation, not a claim.
**No CANOPY measured or computed result appears in this ledger** (the only figures are published literature values or scenario inputs). Spark-dependent rows stay conditional until the [acceptance checklist](SCIENTIFIC_ACCEPTANCE.md) row they cite is `verified`. Record run IDs, inputs, model and environment for every Spark-dependent row and every on-screen or narrated figure in the [Evidence register](#evidence-register) at the end, copied from the protocol §7 run block or the acceptance evidence link, never from prose. Issue comments, laptop or WSL runs and untested draft PRs are never acceptance evidence (G-12).

**Categories:** **VR** verified public research · **RI** verified repository implementation (code inspected on `main` 630ee65 and code pointers re-checked on `main` `ca1662d` on 13 Nov; development tests reported in PR #52 and not re-run here; code that exists only on an unmerged branch is HF until it is on the release SHA) · **SE** actual Spark evidence (pending; a Spark run reported only in an issue comment is "issue-reported", not SE met) · **HF** hypothesis / future capability · **UP** unsupported / prohibited.
**Judging:** I = Impact · T = Technical Execution · F = Feasibility.
