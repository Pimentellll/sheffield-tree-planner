## 2. Impact, Technical Execution and Feasibility (team review text)

**Impact — does it solve a real problem?** Street-tree planting is constrained, public and contested. In Sheffield, street trees are managed under the 2021 Street Tree Partnership Strategy, a sub-strategy of the Trees and Woodlands Strategy 2018–33, through a partnership that brings together the council, its highways contractor, conservation charities and campaign groups ([research §1](IMPACT_AND_FEASIBILITY_RESEARCH.md#1-the-real-problem-in-sheffield)). UK Forest Research notes that urban trees cool both by local shade and by transpiration, and that the benefit depends on placement, species, size and surroundings (ledger I-07); CANOPY computes only the first of these, as direct-sun shade. The practical difficulty is not "plant more trees" but "which positions add useful shade within this budget and these constraints, and can we show why". Shade that duplicates existing building or canopy shade adds nothing. Winter overshadowing can be a cost. Utilities and surveys decide what is deliverable. CANOPY targets that decision step: comparable, explainable options with explicit unknowns. We do **not** claim measured cooling or community outcomes; shade is the first, physically defensible link in that chain ([research §2](IMPACT_AND_FEASIBILITY_RESEARCH.md#2-shade-is-not-cooling-what-the-evidence-supports)).

**Technical Execution — agentic AI and local compute.** The agent is a bounded tool-using loop. The model sees typed tool schemas generated from the backend contracts, chooses an operation, and the host validates arguments, dispatches an asynchronous job, polls it, checks result identity and currentness, and accepts only evidence IDs it actually observed. User-facing figures are generated from stored Results. The model's own wording is kept separately and scored for faithfulness. The model runs locally on the DGX Spark through the organiser-supplied Ollama **[if verified; otherwise only the ledger H-07 wording]**; the numerical engine is a CPU reference implementation (pvlib SPA sun positions, ray–crown intersection, overlap-aware search, independent constraint checker). The five organiser-required tests are scored on eight dimensions and attribute failures to model, host or numerics ([protocol](AGENT_EVALUATION_PROTOCOL.md)). Why deterministic tools: they make numbers reproducible and auditable, and they let us show a model mistake as a model mistake rather than hiding it in fluent text.

**Feasibility — beyond the hackathon.** The contracts already carry several things a real deployment would need: immutable scenario revisions, input fingerprints, source and rights records, survey requirements as explicit unknowns, and human acceptance. Access control, authenticated hosting, governance and change control are still to be built ([research §5](IMPACT_AND_FEASIBILITY_RESEARCH.md#5-staged-adoption-pathway-feasibility), stage 4). The next step is a desk pilot on one real street with rights-cleared geometry and an independent shadow comparison, then an optional radiation/thermal-comfort module (SOLWEIG-class) validated against field data, then integration with survey and highways processes ([research §5](IMPACT_AND_FEASIBILITY_RESEARCH.md#5-staged-adoption-pathway-feasibility)). In a deployment, running the model locally means no hosted model API is called, which matters for council data governance [say "on our DGX Spark" only if X-01/X-02 are verified; network isolation has not been audited].
