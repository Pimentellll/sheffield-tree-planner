## Findings that need team attention (read first)

1. **The 8,192-token rule cannot be enforced or proven by the current client settings alone.** On `main` (`ca1662d`; `agents/__init__.py` is unchanged through `be9d544`) the only client, `LocalClient`, posts to the OpenAI-compatible `/v1/chat/completions` route (base URL must end `/v1`, `agents/__init__.py` L88). Ollama documents that this API has no way to set context size, so `num_ctx` cannot be set per request, and the server default may differ from 8,192. The client's input bound is in **bytes** (`max_input_bytes`), and its token bound needs a trusted counter, which no code on `main` configures. **Update (PR #70 @ `8d24e73`, R03/R25):** Ben's **active lane is the native Ollama `/api/chat` client**, which is to send `options.num_ctx` 8,192 and `options.num_predict` on every request; `/v1` with a Modelfile alias or `OLLAMA_CONTEXT_LENGTH` (FIX-1a) is the **fallback** only. The native client is not on any pushed branch or on `integration/arnav/spark-demo`, so it is unverified. **Compliance must be shown per request from the server-reported counts of whichever transport ran, with the transport recorded:** native `prompt_eval_count` + `eval_count` with the requested `options.num_ctx`, or `/v1` `usage.prompt_tokens` + `completion_tokens`; plus the loaded context from `/api/ps`. Under Ollama prompt (prefix) caching, `prompt_eval_count` may count only newly evaluated tokens (a hypothesis in the merged runtime audit §9, unverified); Ollama's `/v1` `usage.prompt_tokens` may be filled from the same counter, so the `/v1` fallback is not exempt. Until this is checked on the DGX, a low value does not prove compliance. **Validity rule (acceptance X-06; decided 13 Nov by Arnav's coordinating session, Arnav's own confirmation pending):** server-reported prompt + output ≤ 8,192 per request. FIX-1's 7,168-token prompt guard (1,024 reserved for output) is the engineering guard; a guard trip is a host failure, not a breach. The merged runtime audit's R03 (L32) states that stricter guard as engineering policy, and its §9 (L155) names a tokenizer count of the full request or a cold-cache request as alternative proofs; the acceptance row governs run validity. A prompt-count bound alone does not prove nothing was truncated (PR #70 §9 step 4). Ben owns any fix. → [Acceptance X-06](SCIENTIFIC_ACCEPTANCE.md), [Protocol §5](AGENT_EVALUATION_PROTOCOL.md#5-host-versus-model-failure-classification), ledger H-06.
2. **Moving a catalogue tree with `compare_locations` always produces an infeasible diagnostic in the current contract.** `relocate()` keeps the placement's `candidate_id`/`location_id` and moves only its position, so the independent checker records `candidate mismatch`. The old FIVE-03 expectation ("a valid permitted alternative") is therefore wrong. The correct answer is that the moved position is *not* a permitted alternative in this catalogue model. → [Protocol case C3](AGENT_EVALUATION_PROTOCOL.md#c3--compare-an-alternative-placement).
3. **The synthetic "summer shade" is a one-hour, single-instant snapshot.** The seeded scenario has one time bin per case (1 Jul 12:00 UTC, 1 h; winter 1 Dec 12:00 UTC, 1 h). An `additional_shade` value in m²·h is therefore shaded area × 1 h at about solar noon. It is not daily, seasonal or annual shade. The narration must say "one midday sun position, counted for one hour" (acceptance N-02; ledger S-05) or simply "computed geometric shade for the declared time sample", never "shade over the hour". → [Ledger S-05](EVIDENCE_AND_CLAIMS_LEDGER.md).
4. **Say "computed", not "measured", for shade.** Existing drafts ask the agent for "measured shade". Nothing is measured; the values are computed by the deterministic model on synthetic geometry. The frozen prompts here avoid the word.
5. **Weighted utility is not area.** The seed sets target weight 2, so `weighted_shade_utility` (weighted m²·h) should be exactly 2 × `additional_shade` for the single target. Showing the weighted number as "shade area" would double the apparent benefit. → [Acceptance N-03](SCIENTIFIC_ACCEPTANCE.md).
6. **Watch pence versus pounds.** The agent's host-generated summary prints `cost=… pence` (seed: £100 per tree = 10000 pence; budget £200 = 20000 pence). A model narrative that says "£20,000" is a numerical error. → [Acceptance N-04](SCIENTIFIC_ACCEPTANCE.md).
7. **The committed deployment profile is not the evaluated model.** `deploy/spark/model-profile.json` describes a vLLM container serving the Hugging Face BF16 checkpoint as `tree-planner-local` (status `candidate_not_device_tested`). The organisers supply Ollama tags (`nemotron-3-nano:30b`, `nemotron-3.5-lightning:30b`). The form's model field must come from `ollama ps`/`ollama show` on the Spark, not from that file. **Update (PR #70 @ `8d24e73`, R03/R05; #62):** on the active native `/api/chat` lane no alias is needed, because `num_ctx` is set per request; the `/v1` alias route of FIX-1a/FIX-3 is the fallback. If an alias was used, the form and X-02 record the **organiser base tag** behind it (`ollama show <alias> --modelfile`, `FROM` line), never the team-made alias. FIX-3's smoke assertions must match the transport that ships (see the reconciliation note in [ENGINEERING_FIX_PLANS](ENGINEERING_FIX_PLANS.md)). Issue #54 reports (Ben) a chat-only smoke of `nemotron-3.5-lightning:30b` on the Spark with no domain-tool call; that is issue-reported, not verified by us, and is not evidence that the agent ran (ledger H-07).
8. **The existing live test does not test tool selection.** `backend/tests/agents/test_live_local.py` gives the model exactly one operation and an instruction naming it. That proves the transport path, not model choice. The protocol fixes one four-tool set for all five cases.
9. **The seeded demo scene contains no buildings or existing trees, and the winter limit cannot bind.** `backend/src/tree_planner/evaluators/physical_seed.py` (`ca1662d`) sets `"triangles": []` and `"existing_trees": []` (L32–33) and `existing_trees=[]` (L121), so the baseline is unobstructed sky and no demo number shows existing shade being discounted; the B − V mechanism is exercised only in development tests. The winter case exists only when the runtime is seeded with `winter=True` (L38, L227–228). Its limit is `maximum_loss_m2_h=100` (L259), but the receiver grid is 13 × 15 = 195 samples of 0.25 m² (L25, L29–30) with one 1-h bin (L217), so the largest possible loss is 195 × 0.25 m² × 1 h = 48.75 m²·h. If the winter case is shown, say "checked and passing" or equivalent (only once a recorded result shows it; acceptance N-09 stays `blocked` until `--winter` is confirmed in the deployed start command), never that the winter limit shaped the result. → Ledger I-02, S-01, S-06.
