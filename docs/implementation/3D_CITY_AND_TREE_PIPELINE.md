**Status:** implementation proposal for review, **not** a claim of real-site readiness.  
**Date:** 13 November 2026. **Scope:** new geospatial visualisation and tree-identification capabilities with a strict adapter to the existing numerical backend.  
**Ownership:** this document assigns no writer; live issue assignment governs (mapping in §6 and §7). Reviewers by domain: Alex (city frontend/3D interaction); Arnav (geodesy, data semantics, scientific approval); Ben (asset registry, API/job contracts and deploy).

## 1. Problem, desired result and hard boundaries

### Current state (repository inspection, 13 Nov)

- `frontend/src/scene/SiteScene.tsx` is a local Three.js engineering viewer: fixed ground/grid and geometric tree proxies; it supports synthetic reference/physical scenes, candidate markers and evaluated layouts. It is **not** a geospatial, tiled 3D model of Sheffield.
- `frontend/src/scene/transform.ts` uses a provisional ENU → Three.js transform (east, up, −north), and reports incompatible bundle matrices; do not assume all real coordinate frames are supported.
- Unmerged branch `feat/alex/terrain-context-view` (`b1bb0e5`, Alex; #16) adds a display-only EA DTM/first-return DSM crop script (`frontend/scripts/prepare_terrain.py`: rasterio, EPSG:27700 check, SHA-256, licence/attribution, Weston Park 450 m audit buffer, Arts Tower marker) and a Three.js `TerrainView` labelled `VIEW ONLY · NOT ANALYSED`. Its compass is labelled grid north, and its metadata records the ODN vertical datum as publisher-declared, not confirmed from file tags. It has no building or tree layers, and no acquisition receipts or raw tiles are in git.
- `backend/src/tree_planner/site/import_pipeline.py`: `import_pair()` (used only by tests; not exposed by the API) rejects `site_kind != synthetic_test` and any ODN/Newlyn vertical datum. `ImportResult.physical_scene` rejects non-flat terrain, unresolved elevated semantics, missing cells, **any** SiteBundle `existing_trees` feature (Placement correspondence unreviewed) and, separately, DSM vegetation combined with explicit existing-tree Placements. `terrain.py` works on prepared in-memory rasters, **not GeoTIFF ingestion**.
- `POST /api/v1/sites/import` registers a typed `real_site` SiteBundle after asset/fingerprint checks, and `compute_readiness` adds no real-site blocker. Computation is refused by the `site_kind != synthetic_test` gates in `evaluators/physical_runtime.py`, `evaluators/__init__.py` and `contracts/m2.py`.
- `backend/src/tree_planner/site/transform.py` (`BngEnuTransform`) already performs a PROJ-based BNG → true-ENU transform and reports the selected horizontal operation and accuracy (`selected_horizontal_operation()`). It is synthetic-only, requires WGS84 ellipsoidal heights and is explicitly not a SiteBundle affine matrix. BUILD B03 records OS grid/control receipts; the default transform fallback is not accepted.
- The synthetic numerical evaluation/search and typed immutable result/jobbing pathway exist. Real Weston Park/Manor Fields source files, their hashes, accurate datum/semantic mapping, rights and solver parity have not been accepted. BUILD/B08 govern readiness.
- The [13 Nov site audit](../site-audit/STP-005-desk-audit.md) selects **Weston Park** as geometry pilot and **Manor Fields Park** as fallback. Weston Park is a Historic England Grade II registered park and garden (entry 1001340): any planting position needs separate heritage, land-manager, utility, soil and access review. An OSM box is a discovery envelope, **not** surveyed planting land.

### Target user journey

A user opens a georeferenced 3D Sheffield viewer, navigates to Weston Park, displays recorded tree locations and detected canopy (displayed as inferred) separately, selects a feature to read its source and uncertainty, and requests entry into a site-scale planting workspace. A validated scientific SiteBundle is required for real numerical claims; otherwise the UI remains in **real geographic visualisation only** mode with computation disabled/clearly isolated.

**Non-goals for event-day MVP:** a verified whole-city inventory; citywide numerical optimisation; species/health inferred from height alone; raw DSM-labelled pixels as surveyed trees; arbitrary agent access to source files; planting permission; claims about °C cooling, carbon, AQI, runoff or monetary savings based only on geometric shade.

**Priority:** on event day the one-site Sheffield visual pilot is **P2 deferred** until rights and CRS/solver parity pass ([issue index](../EVENT_DAY_ISSUE_INDEX_2026-11-13.md) X-E06; the board's X-E06 row lists it as P1, conditional on source/CRS and visual validity, and the issue index records the current P2 deferral), and the [event-day board](../EVENT_DAY_EXECUTION_2026-11-13.md) defers citywide asset ingestion. Citywide browsing/LOD maps to [FEATURE_PRIORITIES](../FEATURE_PRIORITIES.md) F024 (P2) and F025/F033 (P3) and needs explicit assignment plus a method/data/rights/validation plan before implementation. Do not disrupt the working synthetic demo/Spark delivery to pursue this visual milestone.

## 3. Proposed architecture: one source register, two geometry products

### 3.1 Pipeline stages

1. **Acquisition and custody:** licensed raw asset downloads via human-approved source-list workflows; store raw files outside git, digest SHA-256; record URI, source release, capture date, licence, all four use permissions, required attribution, resolution/coverage, owner and acquisition time. No generic external URL passed by the planning agent.
2. **Verified geodesy:** inspect source coordinate reference system, axis order, precision, units, vertical datum and no-data. EA data are typically BNG/EPSG:27700 with ODN heights. Use an appropriate grid-enabled PROJ transformation (OSTN15/OSGM15 where required), report the selected operation/accuracy and known-point residuals. Do **not** assume a single constant datum offset or equate BNG grid north to true north. Record the full display chain too, with the operation and residual for each step: source BNG/ODN → (OSTN15/OSGM15 grid) → ETRS89/WGS84 → display frame (Web Mercator for a MapLibre view, or the local true-ENU frame for the Three.js scene).
3. **Spatial preparation:** resample/co-register DTM and DSM where necessary with explicit interpolation rules; form coverage masks, capture dates and height residual statistics; handle missing data fail-closed for analysis. Clip a site and independently justified distant shadow context. Never allow a visual tile boundary to truncate an analytical occluder unnoticed.
4. **Semantic separation:** class terrain, building, vegetation and unknown; use rights-cleared footprints/observations and explicit confidence. Height alone is not semantic proof. Keep unknown elevated cells explicit rather than promoting to canopy. **Building heights:** derive each extrusion height as a declared statistic of first-return DSM − DTM within the footprint (e.g. a median with a stated buffer; method approved by Arnav), recorded with method/version and flagged per feature. A footprint without a valid height renders as a flat outline labelled `height unknown`, never with a default height.
5. **Tree inventory fusion:** ingest authoritative recorded points and supplementary detections as **different evidence classes** (§3.2); match using geometry, local uncertainty and source dates; preserve stable IDs and unmatched sources. Never merge overlapping crowns on proximity alone without a recorded association.
6. **Visual asset build:** produce terrain LODs, simplified building extrusions/mesh, 3D-tree instances, feature index, tiles/layers, attributes and source overlay metadata; provide site/high-detail representations, with citywide/coarse levels subject to the priority rule in §1.
7. **Scientific asset build (independent gate):** only from reviewed source geometry, produce receiver samples, static occluders, existing-tree baseline representation, planting regions/exclusions and finite candidate catalogue; register immutable physical scene and exact source fingerprints. A decorative 3D model must never be used as implicit numerics input.
8. **Evaluation/inspection:** inspect-site readiness gates and explicit results connect an accepted SiteBundle to the existing backend; unsupported or non-accepted sites remain visual-only.

### 3.2 Proposed contracts (additive for visual contracts; not existing API)

A versioned `CitySceneManifest` should reference:
- geographic extent, source CRS/datum/operation, local visual origin, units and north convention;
- source hashes and per-asset rights for local use, team sharing, public display and export, reusing the existing `Rights`/`Asset` contracts and `AssetRegistry` (§6) rather than a parallel rights model;
- terrain/buildings/trees/layer tiles and scale/LOD policies;
- feature-index manifest (stable source-backed IDs, geometry type and selection metadata);
- temporal/season coverage and quality, with 'unknown' values preserved;
- inspected/verified status and a labelled relationship to zero or more SiteBundle revisions.

A `TreeFeature` should include stable canonical ID; original source IDs (labelled as service record IDs where they are); `evidence_class`; `match_status`; source and capture date (capture date nullable with an unknown reason, never back-filled from publisher update dates); position and transform identity; optional crown geometry, estimated height and species **only if evidenced**; confidence; match links; baseline occlusion ownership; and complete restrictions/uncertainty.

**Tree vocabulary (proposal; defined here once and cited by PR #67, GEO3D-05, §4 and §8):** two orthogonal fields.
- `evidence_class` ∈ {`recorded_location`, `detected_crown`, `field_verified`}: how the tree is evidenced.
- `match_status` ∈ {`recorded_only`, `detected_only`, `matched`, `ambiguous`, `conflicting`, `not_assessed`}: the Phase 2 matching outcome.

There is no `potential_match` class. An unknown elevated object is a scene-semantic class (terrain/building/vegetation/unknown, §3.1 step 4), never a `TreeFeature`. "Inferred crown" may be used as display text for `detected_crown` only; a detection is never labelled verified (only `field_verified` evidence is).

This is a design seam. Before code, typed API generation/versioning follows the contract owner in the live issue, and Arnav approves spatial/physical meanings. These visual contracts are additive; real numerical use needs a versioned SiteBundle change or a documented pre-reprojection decision (§6). Do not mutate the existing 0.1.0 SiteBundle serialization ad hoc from the browser.

### 3.3 One crown, one baseline occlusion owner

A council point, a detected crown (`detected_crown`) and a rendered tree icon may describe the same physical tree. They do not automatically represent three independent shading blockers. Introduce `baseline_occluder_ref` / `representation_role` and explicitly map each accepted existing canopy component to **exactly one** computational baseline obstruction. If evidence cannot resolve matching, set `match_status` to `ambiguous` or `conflicting` and block affected real-site shade claims rather than double-counting. Today, loading recorded trees as SiteBundle `existing_trees` blocks `physical_scene` export until this mapping is implemented and reviewed (§1).

For a given receiver/time/case and fixed baseline, `additional_shade = shade(baseline + proposals) − shade(baseline)` in declared physical units; weighted utility is a separate quantity. Leaf-off DSM crown geometry cannot be used for leaf-on dates without a documented, tested substitution/assumption.

## 4. Individual-tree identification methodology

**Phase 0 — direct point features:** parse downloaded council ArcGIS features in native `f=json` (EPSG:27700; the catalogue `f=geojson` link reprojects to WGS84, per #69) with actual verified schema, retain source record ID and location, set `evidence_class = recorded_location` (as #69's importer, draft [PR #77](https://github.com/Pimentellll/sheffield-tree-planner/pull/77), already does). That importer emits no `match_status`; the later fusion/adapter step (unassigned) sets `match_status = not_assessed` until Phase 2 runs. Show a point icon with `recorded location; not independently field-verified`. Do not invent missing crown/species/health attributes or a capture date.

**Phase 1 — canopy candidates:** compute CHM = first-return DSM (`FZ_DSM`) − DTM (`F_DTM`) on an identical grid after no-data handling, as elevated-object evidence; record the product/return used for every derived raster. Any use of the last-return DSM (`D_DSM`), e.g. a first−last difference as a penetrable-vegetation indicator, is an optional diagnostic requiring Arnav's method approval and validation. Exclude confidently classified buildings and unsuitable surfaces, run height filtering/segmentation (e.g. local peaks/watershed), and make crown **candidates** (`detected_crown`), not certified trees. Record raster scale, thresholds, algorithm version, scene date and confidence proxies. The 1 m source, overlapping crowns and deciduous leaf-off limitations must be visible.

**Phase 2 — matching:** spatially join candidate crowns with inventory points using documented distance/overlap, positional error and source epoch; preserve every matching outcome (`recorded_only`, `detected_only`, `matched`, `ambiguous`, `conflicting`); `not_assessed` applies only before matching has run. Never silently fabricate a tree or species by nearest-object association. Flag problematic occlusion near buildings and park edges.

**Phase 3 — independent validation:** manually annotate a representative local validation set, including buildings, tree clusters, solitary trees and leaf-off cases, against a reference independent of the EA DSM/CHM: a rights-cleared imagery product with recorded licence, or a dated field walk-over by a named person. Annotation on the detector's own DSM/CHM is circular and does not count. Before any processing, Arnav records the reference, minimum sample size per stratum and minimum precision/recall; below those thresholds detected crowns stay hidden or carry a "not validated" display label (a display flag, not an `evidence_class` value). Report inventory coverage (unknown if not established), crown-object precision/recall, match precision and positional residuals with confidence stratification. Compare to a simple inventory-only baseline. ML detection (imagery/DeepForest) is optional and gated on image rights, locally relevant annotation and evidence of added value; it is not the required first implementation.

## 5. 3D viewer architecture decision

**First visual slice:** build on, or reconcile with, Alex's unmerged `feat/alex/terrain-context-view` Three.js `TerrainView` (#16) before choosing a separate renderer. MapLibre GL JS (terrain if properly prepared, 3D building extrusions and tree feature layers) or a future CesiumJS/3D Tiles viewer are alternatives for the viewer owner to decide if profiling or true city-scale mesh requirements justify them; neither is a mandated dependency change. Retain the current Three.js numerical scene for bounded local planting/evaluation.

LOD (city and neighbourhood levels fall under F024/F025/F033 and the §1 priority rule):
- city: downsampled terrain, generalised buildings, area/cluster canopy (no claims of individual tree identity);
- neighbourhood: more detailed buildings, inventory markers, candidate canopy outlines;
- site: instantiated trees, crown geometry and selectable stable IDs;
- analytical: separately validated geometry, receivers, exclusions and proposed placements.

Feature picking returns stable ID/manifest source refs, **not** a visually guessed instance index. Large tile/asset sets require indexed retrieval, camera frustum/LOD controls, bounded memory and a graceful failed/absent tile state.

Camera: georeferenced north, scale and tilt; visible north reset and 2D/3D camera modes where implemented. The north indicator stays labelled grid north until grid convergence at the site origin is computed and applied (GEO3D-03). City-to-site transition preserves selection and geography; demonstrate with known points and metre-scale objects. Browser GPU rendering is **not** DGX Spark GPU numerics.

## 8. Required tests

**Data:** invalid CRS, wrong axis, missing OSTN/OSGM resource, unknown vertical datum, mismatched pixel grids, no-data strip, stale/duplicate source ID, rights restricted/unknown, capture-epoch mismatch or absent capture date, semantic unknown, building footprint without valid height. All produce explicit typed failures or visually limited data.

**Tree matching:** each `match_status` value (`recorded_only`, `detected_only`, `matched`, `ambiguous`, `conflicting`, `not_assessed`), overlap, ambiguous multi-crown, building false positive, positional offset, leaf-off absent crown, tree removed after source epoch, protected/plantability unknown. Preserve original records for audit; never convert an inventory gap to absence.

**Rendering:** terrain height and north control vs known reference (grid vs true north labelled); camera and identity persistence across LOD; tile error; stable feature picking; icon/outline for each `evidence_class`, with `match_status` shown in the inspector (PR #67 §3); 2D/3D mode correctness; responsive and reduced-motion alternatives.

**Numerics:** non-flat placement z; terrain intersection; static building/vegetation shading with identical baseline; directional context; measured receiver triangle area; one-crown-one-occluder; incomplete data blocked; comparison same inputs; no phantom cooling/thermal/flood result; visual-to-physics geometry parity.

**Ownership:** reviewers Arnav (science), Alex (visual), Ben (API/source); exact branch SHA, data receipts, measured validation and non-deceptive UI screenshot attached to the eventual implementation PR. Production merge follows [AGENT_EXECUTION_PRD](../AGENT_EXECUTION_PRD.md) and BUILD gates. This document alone does not authorize a code merge or a real-site claim.
