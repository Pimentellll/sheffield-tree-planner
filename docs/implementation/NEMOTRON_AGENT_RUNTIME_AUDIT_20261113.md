## 1. What is genuinely implemented

- **Domain:** synthetic SiteBundle, source rights, immutable accepted scenario revisions, layout registration, finite candidate catalogue, strict Pydantic operation arguments, SQLite jobs and Result provenance; physical evaluator/search and comparison are real CPU calculations on **synthetic flat geometry**.
- **Agent core:** `LocalClient` calls loopback `/v1/chat/completions`; `AgentLoop` derives tool schemas, checks strict arguments, pins accepted context and revalidates current Results before presenting authoritative backend text. `HTTPDispatcher` restricts localhost and pins task headers. These are useful defenses, not a finished agent web product.
- **Gaps proven by source:** `api/app.py` exposes `/api/v1/operations` (domain dispatcher) and `/jobs` but **no /agent-runs endpoint**; `frontend/src/panels/CompareScreen.tsx` explicitly says the agent panel is unavailable. `LocalClient` has no mandatory exact input-token counter (optional `max_input_tokens`); full Result is appended as a model observation. The worker-thread loop closure inside `JobWorker.start()` does not catch `JobStore.claim()` / `run_one()` exceptions, so a claim-path invariant error may terminate the worker. `deploy/spark/model-profile.json` is a candidate **vLLM** profile, not the organiser-provided Ollama deployment.
- **Already tracked.** Ben: #54 integrated DGX agent release, #59 public-history security, #62 context, #63 five-case driver, #64 actual Ollama configuration, #65 optional catalogue relocation, #72 worker supervision/clock regression, #73 durable agent-run API. ## 3. Runtime seam: additive contract proposal, not an implemented endpoint

Do **not** expose raw `AgentLoop` or allow the browser to supply `model_base_url`, system prompts, arbitrary tools or unaccepted site identifiers. The trusted server chooses installed provider, session capacity, prompt template, tool allow-list and accepted task snapshot. Add a small manager around the existing loop; prefer its already developed local analogue after Ben reviews it.

Suggested typed contract (a proposal only; final names follow Ben's generated OpenAPI in #73, and the companion frontend handoff in PR #71 uses the same field names):

```text
POST /api/v1/agent-runs
  Body: { request_id, accepted_scenario_ref, user_text, requested_intent? }
  If-Match: "<accepted revision>"
  202:  { agent_run_id, accepted_scenario_ref, status: "queued" }
GET /api/v1/agent-runs/{agent_run_id}
  200:  { agent_run_id, status, accepted_scenario_ref, created_at_utc,
          updated_at_utc, events: [sanitised event], job_ids, validated_run_ids,
          host_summary?, untrusted_model_narrative?, reason_code?,
          model_identity?: { model_tag, provider, release_sha? },
          source_snapshot_hash? }
POST /api/v1/agent-runs/{agent_run_id}/cancel
  200:  { agent_run_id, status: "cancellation_requested" | "cancelled" | terminal }
```

Reload and history also need a way to find a run again: either a lookup by the client's `request_id` (which also serves the lost-POST case R11) or a list route scoped to the accepted scenario. Ben decides which in #73; the frontend must not invent one.

No new `ScenarioInput` or `Result` wire fields for the hackathon. When domain operations complete, resolve their **existing** Job/Result separately and validate `validate_delivery_currentness`. `agent_run_id` represents an investigation session; `run_id` already identifies a numerical computation, so never alias them. An agent session may contain several jobs, including failed ones.

**Run state machine:** queued → running → {completed_with_evidence, metadata_only, draft_prepared, clarification_requested, safe_abstention, needs_evidence, failed, stopped, exhausted, cancelled}. `cancellation_requested` is transient only. Mapping from the existing `AgentLoop` `Outcome.status`: `completed` → `completed_with_evidence`; `metadata_only` (after `inspect_site`) and `draft_prepared` (after `prepare_scenario`) pass through unchanged; `needs_evidence` stays `needs_evidence` unless the host rubric check reclassifies it as `clarification_requested` or `safe_abstention`; `stopped`, `exhausted` and `failed` pass through unchanged. Clarification/abstention categories are **presentational and independently checked against host rubric**; do not claim a success grade merely because the model says "I do not know". A late numerical Result can stay in domain history but must not make a cancelled/superseded agent current.

**Recorded event (minimal, safe):** sequence; type `model_call | tool_requested | tool_accepted | job_queued | job_running | result_validated | terminal | error`; UTC; registered operation; validated argument digest; exact scenario ref; job/run IDs; bounded host summary; trust label (model statement vs backend result). Never return raw local paths, credentials, unrestricted source rows or arbitrary model-supplied HTML.

**Implementation location (#73):** a narrow `backend/src/tree_planner/agents/runs.py` SQLite-backed manager behind `api/app.py` is acceptable if Ben's existing isolated branch is compatible; use API-generated OpenAPI/TS contracts, not a handwritten divergent interface. Derive `max_actions`, deadlines, model tag and allowed operations from server configuration. If critical integration fails, retain the working deterministic manual simulator and show "agent unavailable", not a scripted substitute.

## 4. Worker and concurrency tests Ben should add before the final freeze

Tests 1–3 belong to #72; tests 4–8 and 10 to #73; test 9 to the existing agent policy tests.

1. **Clock regression:** monkeypatch the clock to return a time before a queued job's `created_at_utc` at claim. Assert no validation exception/thread disappearance; `started_at_utc` is valid and `deadline` semantics remain correct; second queued job completes. Do not hide wall-clock uncertainty by altering stored `created_at_utc`.
2. **Thread exception supervision:** inject a controlled `run_one` failure. Assert either bounded recovery with an explicit health fault or fail-closed refusal; no infinite hot loop and no "healthy" status while dead.
3. **Restart:** lease-gated startup recovery that marks abandoned running jobs `WORKER_INTERRUPTED` already exists and is tested (`test_jobs.py::test_deadline_cancel_recovery_and_invalid_result`, `test_app.py::test_startup_recovery_requires_lease_and_does_not_touch_live_records`). Extend those tests rather than duplicating them, to also assert that completed Results and request identities are preserved and that recovery never reruns a previously admitted operation.
4. **Cancellation:** start model, cancel before tool; start tool then cancel; cancel after terminal. No new request after stop; historical immutable result may exist but not be current.
5. **Lost POST response:** submit succeeds but HTTP response is dropped. Client re-queries saved request/agent ID; no second execution with new random request ID.
6. **Cross-revision race:** accept revision n+1 while model is returning n's result; stale evidence retained as history and not presented as current.
7. **Token context:** mocked missing usage/negative usage/oversized prompt/large search result and actual on-Spark `/api/ps`. Exact token counts are measured, not estimated from characters.
8. **Parallel session:** two browser users click run; server enforces capacity=1 for P0, retains typed "busy" or queued status, and keeps watchdog responsive.
9. **Prompt injection:** malicious source text attempts to alter budget/approve planting/read files; model is not permitted to do so even if it requests the action.
10. **No-answer/ambiguity:** one run with no tool and correct abstention; one with prohibited invented number. Host records both, preserves model text separately, never counts either as evaluated physical result.

Use the existing `backend/tests/agents` mocks, `test_live_local.py` recorder, `backend/tests/jobs` and `backend/tests/benchmarks` infrastructure. **A green synthetic test suite is not a Nemotron proof.** Do not run competing GPU benchmarks during Ben's deployment window.

## 9. Critical late-cycle transport finding: native Ollama messages are not OpenAI wire messages (R25 P0)

**Verified against primary Ollama documentation on 13 Nov:** [Native chat endpoint](https://docs.ollama.com/api/chat) and [Tool calling examples](https://docs.ollama.com/capabilities/tool-calling). This is a **source-shape incompatibility requiring an adapter test**, not proof that Ben's unpublished native adapter is broken.

- Ollama POST `/api/chat` accepts `tools`, `messages`, `stream:false`, runtime `options` (including context configuration supported by the chosen model), and `think`. It returns a top-level `message` and `done` / `done_reason`, `prompt_eval_count` / `eval_count`, nanosecond durations. The existing `LocalClient` requires exactly one OpenAI `choices[]` entry with `finish_reason` in {`stop`, `tool_calls`} and an assistant `message`; it does not read `usage` (FIX-1b proposes `usage.prompt_tokens`). No field-name equality should be assumed.
- Official Ollama tool call samples give `function.arguments` as a **JSON object**, not a JSON string, and use `function.index`. The documentation samples omit an OpenAI-style `id`; Ollama's native `ToolCall` type has an *optional* `id`, and recent versions are reported to populate it, so record the installed `/api/version` and the actual shape in a DGX receipt rather than assuming either. Existing `AgentLoop` requires each call to be a dict with `type == "function"`, a string `id` and a dict `function` (`agents/__init__.py` ~608–614), and `parse_arguments()` requires JSON text. Native response tool calls carry no `type` field. Naively passing a native `message` into this loop would reject real tool calls.
- Ollama's documentation examples send tool replies as `{role:"tool", tool_name:<registered tool>, content:<text>}`, whereas the existing internal loop uses OpenAI-style `{role:"tool", tool_call_id:<id>, content:<text>}`. The native message type also accepts an optional `tool_call_id`. Send **both** the registered `tool_name` and the correlated `tool_call_id`, keep results in call order, and preserve the association of each (possibly parallel, possibly same-named) tool request and observation across turns.
- The response lacks a directly equivalent `finish_reason:"tool_calls"` guarantee. Use validated presence of `message.tool_calls`, `done:true` and an explicit allowlist of `done_reason` states; reject incomplete/length/truncated and malformed returns, rather than inferring success from HTTP 200. Confirm the actual loaded model/provider response in a private DGX receipt.
- Native `prompt_eval_count` is the model-server-reported prompt token count per request. Record it and bound it with reserved output budget; do not confuse it with `eval_count` (generated tokens) or use bytes/characters as exact token counts.

### Required small adapter design (Ben's native client, #54/#62; consumed by #73)

Maintain a single internal strict `AgentLoop` protocol and add **explicit bidirectional normalisation** in the native `/api/chat` client:

1. **Request:** Convert internal assistant tool-call messages + tool observations to valid native Ollama chat history, mapping one internal tool call to its named tool result. Any missing/ambiguous association is a protocol error; no silently dropped tool context. Preserve original tool name; never use model text as an endpoint or arbitrary tool name.
2. **Response:** Validate top-level `done` / `done_reason`, assistant role and one supported message shape. Decode the entire native response body with the existing strict `_json` decoder (duplicate-key and nonfinite rejection) **before** any conversion: re-serialising an already-decoded dict cannot detect duplicate keys. Set `type: "function"` on every native call, and reject a call whose `type` is present but is not `"function"`. Convert native object arguments to **canonical JSON text** using `json.dumps(allow_nan=False)`, then rely on the existing `parse_arguments` and Pydantic validation; registered-name allow-listing stays in `AgentLoop`. Native object arguments are not a bypass to looser validation.
3. **Identity:** Use a native `id` when it is a non-empty string not already used in this agent session. When it is missing or empty, derive an **opaque host-side ID unique within the agent session**, keeping the map to `function.index`/order and tool name; reject a duplicate id. Document host IDs as transport correlation identifiers, **not model-provided authority**. Never let one id correlate two calls or apply a tool observation to another call.
4. **Usage:** Send `options.num_ctx` = 8192 and `options.num_predict` on every request. If the installed Ollama supports disabling silent history truncation and context shifting (`"truncate": false`, `"shift": false` on `/api/chat`), send both, treat the resulting error as a typed fail-closed `context_exceeded` with no dispatch, and never retry with truncation enabled. **Prove on the DGX** with an over-cap history that the installed version (record `/api/version`) refuses rather than truncates; if it cannot be made to refuse, fail closed on the bound below and record the limitation. Save actual `prompt_eval_count`, `eval_count`, configured `num_ctx`/`num_predict`, loaded-model context from `/api/ps` or equivalent, model tag and precise release SHA. Fail closed when the configured cap cannot be established. A `prompt_eval_count` bound is a second check, not proof that nothing was truncated, because a truncated history reports the truncated count.
5. **Negative tests:** native single tool, native id present and preserved, parallel tool indices/association (including two calls to the same tool correlated by id), missing id, duplicate id, missing `type` normalised and unknown `type` rejected, duplicate argument keys in the raw body, object arguments, over-cap history with truncation disabled → error and no dispatch, unknown name, malformed args/float NaN, absent/missing usage, `done:false`, context overage, reply history across two model turns, tool-result order swapped and error/no-tool abstention. Confirm no double-dispatch under an ambiguous HTTP response.
