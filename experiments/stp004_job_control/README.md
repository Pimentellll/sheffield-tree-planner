# STP-004 synthetic job-control probe

This independent local experiment uses opaque synthetic input identities and result tokens. It is not a production Job, Result, API, worker, evaluator, or serialization contract. It starts from integration revision `c94a5d2e86a30b2d04481aaf593bfd3c1af51713`, informed by the unaccepted draft CONTRACTS blob `c6ac67c7fb1f3e9436499b8270095464eacbf533`, sections 5 and 9. No shared contract or release version changes are proposed.

From the repository root, run with Python 3.11 or newer:

```powershell
python -m unittest discover -s experiments/stp004_job_control -v
```

Tested locally with CPython 3.11.15 and 3.12.13 on Windows; the 3.11 environment uses SQLite 3.53.1. The probe tests also run through the exact CI step locally. Existing Windows/Ubuntu CI runs the probe when its directory is present and fails if discovery is empty or a test fails; this is not application acceptance. Tests create temporary databases under `TMPDIR` when supplied and close their connections. This probe uses caller-supplied normalized payload and full fingerprint identities; it does not construct or validate domain fingerprints. Operation plus request ID is unique in this experiment; no claim is made about cross-operation request-ID scope in a future contract. Matching payload, full fingerprint, operation and scenario identity is required for reuse, not a geometry key. Source runs are synthetic opaque tokens, not numerical fixtures or Sheffield data.

SQLite is tested because durable records and atomic read-modify-write across independent connections are the question here; a process-local dictionary and lock cannot establish persistence or coordination across connections/processes. This does not choose a production backend. Each write transaction explicitly uses `BEGIN IMMEDIATE`, commit and rollback; SQLite may return busy if ownership cannot be obtained before the connection timeout. See [Python 3.11 sqlite3 transaction control](https://docs.python.org/3.11/library/sqlite3.html#sqlite3-controlling-transactions) and [SQLite transactions](https://www.sqlite.org/lang_transaction.html).

The configured limits count records, not processes; all cooperating stores must use the same configured limits. Cache delivery performs a queued-to-running-to-completed bookkeeping transition atomically without taking a worker slot. Cancellation and deadline expiry acknowledge bookkeeping state only and do not physically stop an uncooperative CPU evaluator. Deadline-bound live completion and cache delivery require a finite caller-supplied clock and cannot publish success at or after the deadline. Time values must survive SQLite `REAL` storage exactly: lossy integer deadlines/clocks are rejected before mutation, and accepted deadlines are bound as validated floats so identical retries preserve their boundary. A regression first reproduced the late-completion bug, then verified persisted `DEADLINE_EXCEEDED`, no result promotion, no fallback and unchanged cached-source provenance. Explicit expiry is still a caller action, not a background timer or hard execution deadline. Opening another connection never triggers recovery. `recover_exclusive_startup` requires the caller to ensure no prior workers are live; it fails running records, preserves queued and terminal records, and is not a lease or distributed ownership mechanism. History records state and ignored terminal callbacks. No timestamps or production progress/error envelope are claimed.

No HTTP, domain validation, asset rights, physical computation, scientific evidence, real site, model, or hard CPU cancellation is provided. Independent source review, STP-001 owner acknowledgement and STP-002/003 integration decisions remain required before any production contract or dependent implementation is accepted. This is advance development; event eligibility remains unresolved. This experiment does not complete STP-004 or M2.
